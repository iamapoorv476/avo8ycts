# Design decisions & debugging notes

This replaces the earlier, more detailed development log (`PROGRESS.md`). I've kept the parts that are most useful for a reviewer: the architectural decisions that aren't immediately obvious from the code, and the debugging stories that show how issues were found and fixed.

## Architecture

- **Precompute at ingest, read-only API.** Forecast matching, metric calculations (MBE/MAE/RMSE/σ), and risk-floor calculations all happen offline in `ingestion/run_ingestion_pipeline.py`. The three API endpoints (`docs/api.md`) only read the results that have already been computed. They don't recalculate anything when a request comes in. For a trading-desk tool, responses should be fast and deterministic rather than running statistical calculations every time someone opens a page. There is one documented exception: `/metrics` calculates the exclusion-reason breakdown using a simple `GROUP BY` on an already-precomputed column. This doesn't introduce any new business logic.
- **Idempotent raw ingestion.** `ingest_elexon.py` uses `INSERT OR REPLACE` with natural primary keys. This means the ingestion script can be run again safely, for example, after a schema change, without needing migrations for the scope of this project.
- **Single SQLite file, no connection injection.** There's one pipeline and one database, so adding a dependency-injection layer just to pass around the connection would be unnecessary complexity at this stage (YAGNI). Tests that need a real file-backed database seed and clean up `db.connection.DB_PATH` directly.
  - **Known tradeoff of this choice:** because the project uses a single database file, `test_run_ingestion_pipeline.py` and `test_api.py` seed and tear down that same file, which is also used by real ingestion. Running `pytest` after a real `ingest_elexon.py` or `run_ingestion_pipeline.py` execution deletes the real data because fixture teardown unlinks `DB_PATH`. The API server then opens a new, empty file without a schema and returns a 500 error with `no such table`. This isn't an application bug, but it does affect the development workflow. The fix is to run ingestion again before serving the API. The workflow is: ingest → demo/serve; if you run `pytest` in between, re-ingest before serving again. Using a separate database path for tests would avoid this, but wasn't worth the extra complexity for this project's scope.

## The WINDFOR bug: silently wrong data, not an error

This was the most serious issue I found during development. It also showed why a pipeline completing without exceptions doesn't necessarily mean the data is correct.

**What happened:** `ingest_elexon.py` originally queried `/datasets/WINDFOR/stream` using `from` and `to` parameters, based on the documented convention for similar endpoints. A run against the live API completed without errors, but the downstream results didn't look right (`risk_floor_rows_backfilled: 0`). Instead of relying on the successful run, I checked the raw table directly. That revealed the problem: every row had the same `publishTime`, which was the exact time the request was made, regardless of the requested `from` and `to` range.

**First hypothesis (wrong): range too wide.** I initially suspected the requested date range was too large, so I tried fetching smaller chunks, eventually down to one day. Every request, including the smallest one, returned the same current-snapshot data. This ruled out the range size as the cause rather than fixing the issue.

**Root cause, found by checking the authoritative source:** Instead of trying more variations, I checked Elexon's Swagger documentation for this specific endpoint. The actual parameters for `/datasets/WINDFOR/stream` are `publishDateTimeFrom` and `publishDateTimeTo`, not `from` and `to`. The endpoint doesn't return an error for unrecognized parameters. It silently ignores them and falls back to the current live snapshot. As a result, the pipeline had been completing successfully while processing the wrong data.

**Fix:** I corrected the two parameter names and removed the chunking, which was no longer needed. A single correctly formed request returned the full historical window. I also kept a permanent `_sanity_check_windfor_rows()` guard that raises an error if any fetched `publishTime` falls outside the requested window. This provides a simple check against the same issue happening again.

**Lesson, stated plainly:** An earlier note in this project claimed that the `from` and `to` parameters had been "verified against real sample data." That conclusion came from looking at the shape of a response, which contained several forecast vintages within roughly the expected window, without checking the actual request URL that produced it. The output looked plausible, but that wasn't enough to establish which parameters were working. Once the first hypothesis failed, I checked the endpoint's own Swagger documentation instead of making another assumption based on the response.

## A second, smaller gap found during API design

While designing the `/forecast-detail` endpoint, which needs to expose the forecast's audit-trail `publishTime`, I found that `matched_series` wasn't actually storing that value. `DecisionTimeForecastBuilder` calculated it in memory, but `SeriesMatcher` only persisted `forecast_mw` and discarded the remaining information.

I fixed this by adding a `source_publish_time` column and persisting the value when building the matched series. Reconstructing it when the API received a request would have moved business logic back into the API layer, which goes against the architecture described above.

## Finding, not a bug: a consistent forecast bias in the real data

The full January 2026 `metrics_summary` shows an MBE of approximately +1,840–1,900 MW across the month, indicating consistent over-forecasting. MAE is also close to MBE in magnitude, which suggests that the error is driven more by systematic bias than by random variation.

I checked the underlying data manually before accepting this result. The step-hold resampling is correct, with identical `forecast_mw` values across the two half-hours of each hour. Actual generation varies naturally, and the values are physically plausible for GB-scale wind generation (13,756–19,643 MW).

A likely explanation is that `FUELHH`'s wind `generation` figure covers only Balancing Mechanism-registered or transmission-connected wind, while `WINDFOR` forecasts may cover the whole system, including embedded and distribution-connected capacity. In that case, the two datasets represent different scopes of wind generation rather than a calculation error.

## Day 3

**React dashboard: a real threading bug that `TestClient` never would have caught.**

- Built the dashboard as a single-viewport "trading terminal" with a dark theme, a Recharts chart showing forecast, actual, and floor lines, peak-window shading, four derived-metric cards, and an advisory panel. This replaced the originally planned two-page navigation because the demo recording shouldn't require switching pages midway through. Every number displayed is either returned directly by one of the three API endpoints or calculated on the client using a simple arithmetic operation on returned values, such as a ratio or percentage difference. Nothing is made up. I deliberately avoided showing a recommendation like "procure +450 MW of thermal backup" because the project doesn't calculate required backup capacity. Displaying such a figure would mean inventing a number in a tool that's supposed to demonstrate data accuracy.
- **Verification, from basic checks to a real browser test:** Started with `tsc` and `vite build` to catch type errors, then called the three endpoints directly with `curl` to check their response shapes. Finally, I started the actual backend and Vite development server together, loaded the dashboard in a real headless browser, checked the console, and captured a screenshot. That final step caught an issue the earlier checks had missed: calling `/api/v1/forecast-detail` from a real browser immediately returned a 500 error with `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`. All 26 tests had passed, and `curl` had returned valid JSON just minutes earlier. Neither test exercised FastAPI's real threadpool behavior in the same way as a running server.
  - **Root cause:** FastAPI runs the setup code of a synchronous generator dependency (before `yield`) and its teardown code (after `yield`) through anyio's threadpool. It doesn't guarantee that both operations run on the same worker thread. By default, SQLite connections are tied to the thread that created them. This meant `api/deps.py` could call `conn.close()` on a different thread from the one where `db.connection.get_connection()` had called `sqlite3.connect()`. SQLite rejected that operation.
  - **Fix:** Added an optional `check_same_thread` parameter to `get_connection()`, defaulting to `True` so all existing callers remain unchanged. The ingestion scripts and tests run in a single thread and don't need different behavior. `api/deps.py` is the only caller that passes `check_same_thread=False`. This is safe in this case because the connection is scoped to one request and isn't shared across requests. I then tested all three endpoints with repeated real HTTP requests, which returned 200 every time. I also reloaded the dashboard and checked that the browser console had no errors. This included testing the date picker, confirming that it triggered a new fetch and updated the Y-axis, cutoff, and audit timestamps, and hovering over the chart to check the custom tooltip.
- A smaller visual issue was caught during the same browser-based verification. The peak-window `ReferenceArea` shading was barely visible against the dark background with the initial opacity setting. The TypeScript checks and production build passed, but the shading was difficult to see in the actual dashboard. I only caught it by inspecting the rendered screenshot.
